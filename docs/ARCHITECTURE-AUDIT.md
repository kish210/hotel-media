# نقشهٔ معماری و audit — پیش از بازسازی محصول

> این سند **پیش از هر تغییر کدی** و از روی خودِ مخزن و سرور تولید نوشته شده، نه از روی حافظه.
> هدفش پاسخ به بند ۱۳ مشخصات است: «اول مخزن را بررسی کن، نقشهٔ معماری بساز، بعد مرحله‌ای پیاده کن.»
>
> تاریخ audit: ۱۴۰۵/۰۷/۱۳ · نسخهٔ پایه: `v1.10.3`

---

## ۱) محصول در برابر کد

مشخصات می‌گوید این یک **پلتفرم رسانهٔ هتل** است، نه فقط یک CMS تابلو. کد از قبل بیشتر این
قطعات را دارد — مشکل **نبودِ قابلیت** نیست، **پراکندگی و نمایان‌نبودن** است:

| حوزه | وضع کد |
|---|---|
| تلویزیون اتاق / IPTV | هست و کار می‌کند (پورتال مهمان، منو، اتاق، PMS) |
| Live TV | هست روی TVHeadend + multicast؛ ولی زنجیرهٔ منبع→کانال→گروه ناقص |
| VOD | جدول و آپلود هست — **ولی هیچ پردازشی ندارد** (بند ۳ پایین) |
| تابلو (Signage) | هست و پخته‌ترین بخش است |
| تبلیغات | جدول `campaigns` هست، گردش‌کار کمپین نیست |
| صفحهٔ عمومی/آسانسور | از `venues.kind` درمی‌آید، ولی در UI جدا نیست |
| مدیریت ناوگان پلیر | قوی: ثبت خودکار، heartbeat، صف فرمان، قابلیت per-platform |
| EPG | هست (`epg_sources`/`epg_programs`/`epg_channel_map`) |
| ترنسکد | هست — **ولی VOD از آن استفاده نمی‌کند** |
| پخش اضطراری | `emergency_broadcast` روی صفحه + WebSocket هست |

**نتیجه:** این کار یک **بازچینش و اتصال** است، نه بازنویسی. هیچ زیرسیستم کارکننده‌ای
نباید فقط به‌خاطر UI بد عوض شود.

## ۲) موجودی

- **۴۳ کنترلر وب** · **۳۲ کنترلر API** · **۲۷ سرویس** · **۵ مدل** · **۱۰ پروفایل پلیر**
- **۹۰ جدول** دیتابیس · ۴۶ migration اعمال‌شده

مدل‌ها فقط ۵ تا هستند (`Media`, `Playlist`, `Schedule`, `Screen`, `User`) و بقیهٔ دسترسی
داده مستقیم با SQL در کنترلرها/سرویس‌هاست. این عامدانه نگه داشته می‌شود — بازنویسی لایهٔ
داده در این بازسازی جایی ندارد.

## ۳) یافته‌های اصلی (به ترتیب اهمیت)

### ۳.۱ VOD هیچ پردازشی ندارد — و خودش را «آماده» اعلام می‌کند
`VodController::upload()` فایل را جابه‌جا می‌کند و بی‌درنگ `status = 'ready'` می‌گذارد.
هیچ probe، هیچ بررسی سازگاری، هیچ ترنسکدی. یعنی یک فیلم H.265 یا `.mkv` در فهرست
«آماده» می‌نشیند و روی تلویزیون هتلی پخش نمی‌شود — همان مشکلی که برای تابلو با
`MediaConvertService` حل شد و برای VOD حل نشده.

### ۳.۲ پنج مسیر جداگانهٔ ffmpeg
| جا | کار |
|---|---|
| `TranscoderService` + `TranscoderCommand` (+ `transcoder_jobs`) | Live |
| `MediaConvertService` | آپلود رسانهٔ تابلو |
| `CameraService` | RTSP→HLS دوربین |
| `VodController` (درون‌خطی، خط ۴۱۲ و ۴۲۵) | تبدیل TS |
| `IPTVController` | تشخیص/اجرا |

مشخصات (§۴) می‌خواهد ترنسکد **یک موتور واقعی** شود. پس این‌ها باید به یک سرویس
واحد با مدل وضعیت `QUEUED/PROCESSING/READY/FAILED/CANCELLED` برسند — و
`transcoder_jobs` که از قبل هست، همان جای درست است.

### ۳.۳ سه راه برای وصل‌کردن پلی‌لیست به صفحه
`schedules` (۱۳ ارجاع) · `screens.current_playlist_id` · `screen_playlists` (**۰ ارجاع، مرده**).
اولویت در `Screen::getCurrentPlaylist()` اصلاح شده (برنامهٔ مخصوص صفحه ← انتخاب صفحه ←
برنامهٔ همگانی). `screen_playlists` باید حذف شود.

### ۳.۴ مدل Zone از قبل هست، ولی اسمش Zone نیست
| جدول | واقعاً چیست | نقش در Zone |
|---|---|---|
| `locations` | **شعبه/ملک** (آدرس، شهر، کشور، timezone) | والدِ Zone |
| `venues` | **محل درون هتل** (`kind`, `floor`, ظرفیت، ساعت کار) | **همین Zone است** |
| `screen_groups` + `screen_group_members` | گروه‌بندی آزاد صفحه‌ها | عضویت چند‌به‌چند |

**تصمیم:** Zone جدید ساخته نمی‌شود. `venues` همان Zone است و در UI با همین نام
عرضه می‌شود؛ عضویت از `screen_group_members` می‌آید.

### ۳.۵ دوازده جدول مرده
`corp_departments` · `fids_airlines` · `fids_flights` · `media_subtitles` · `monitor_*` ·
`refresh_tokens` · `retail_products` · `screen_heartbeats` · `screen_playlists` ·
`transport_schedules` · `user_tokens` · `ws_connections`

نکتهٔ صادقانه: `media_subtitles` را خودم در migration 039 ساختم و هرگز وصل نکردم —
زیرنویس رسانهٔ تابلو هنوز پیاده نشده است.

### ۳.۶ سه جدول پرواز
`flights` (**زنده و درست**، ۷ ارجاع، مصرف‌کننده `SignageContentService`) ·
`fids_flights` (۰ ارجاع، مرده) · `inflight_flights` (۲ ارجاع، سناریوی داخل هواپیما).
`fids_flights` باید حذف شود.

### ۳.۷ دو جدول heartbeat
`heartbeats` (زنده) · `screen_heartbeats` (مرده).

### ۳.۸ ناوبری مفاهیم فنی را لو می‌دهد
منوی فعلی «هدِند (TVHeadend)»، «ترنسکد»، «multicast» را به مدیر هتل نشان می‌دهد.
مشخصات (§۱) صریحاً این را رد می‌کند.

## ۴) آنچه باید دست‌نخورده بماند

این‌ها کار می‌کنند و در بازسازی فقط **زیر UI تازه** می‌روند:

- ثبت خودکار دستگاه (`/tv` + `enrollment_tokens` + رنج IP مورد اعتماد)
- heartbeat و صف فرمان (`screen_commands`) و تشخیص تغییر پلی‌لیست با `playlist_rev`
- قابلیت per-platform در `DeviceService::CAPABILITIES`
- ده پروفایل پلیر، از جمله جداسازی Orsay/Tizen
- multicast و API کامل TVHeadend (ضبط، تایم‌شیفت، تگ)
- پورتال مهمان، خدمات، صورتحساب، خروج سریع، PMS
- `SignageContentService` و انواع محتوای تابلو
- `cron-run.sh` و نمایانی خطای کارهای زمان‌بندی‌شده

## ۵) نقشهٔ مرحله‌ای

| فاز | کار | ریسک |
|---|---|---|
| ۱ | معماری اطلاعات و ناوبری تازه؛ پنهان‌کردن مفاهیم فنی زیر «تنظیمات/زیرساخت» | کم |
| ۲ | صفحه‌ها + Zone (روی `venues`) + مدیریت پلیر؛ انتشار به Zone | متوسط |
| ۳ | کتابخانهٔ رسانه + پلی‌لیست + زمان‌بندی | کم |
| ۴ | Live TV: منبع→کانال→گروه کانال→EPG→پروفایل پخش | متوسط |
| ۵ | VOD + خط لولهٔ ترنسکد + HLS + وضعیت پردازش ← **بیشترین ارزش** | بالا |
| ۶ | تجربهٔ تلویزیون مهمان (جدا از تابلو) | متوسط |
| ۷ | تبلیغات و کمپین | متوسط |
| ۸ | مانیتورینگ + پخش اضطراری | کم |
| ۹ | صیقل، دسترسی‌ها، کارایی | کم |

### قواعد اجرا
1. هر فاز = کامیت(های) جدا + `php -l` + بازرس ES5 تلویزیون + تست دود روی سرور.
2. هیچ API موجودی بی‌دلیل شکسته نمی‌شود؛ مسیرهای قدیمی در صورت نیاز alias می‌گیرند.
3. هر تغییر اسکیما یک migration شماره‌دار و روادار (idempotent) دارد.
4. جدول مرده فقط پس از اثبات ۰ ارجاع حذف می‌شود و در همان کامیت مستند می‌شود.
5. UI جعلی ساخته نمی‌شود: اگر backend هست، UI به همان وصل می‌شود.
